1. Introducción

Inicio del proyecto: 13 de marzo de 2025

Este sistema es una aplicación de gestión de proyectos desarrollada con FastAPI, Jinja2 y Tailwind CSS. Permite la creación y gestión de proyectos, tareas, equipos y usuarios con un sistema de permisos basado en roles y propiedad de proyectos.

2. Sistema de Autenticación

Implementado: 15 de marzo de 2025

Credenciales por Defecto

Nota de Seguridad: Las credenciales de administrador se configuran mediante variables de entorno para mayor seguridad.

Variables de entorno disponibles: ADMIN_USER y ADMIN_PASS

Importante: Cambiar las credenciales por defecto antes de desplegar en producción.

Métodos de Login

Login básico: 15 de marzo de 2025 | Integración externa: 20 de abril de 2025

1. Login con Parámetros GET (Integración Externa)

GET /login?username={username}&password={password}
  • Si hay un usuario previamente autenticado, se desautentica automáticamente antes de intentar el nuevo login
  • Si las credenciales son válidas, redirige a / (dashboard)
  • Si las credenciales son inválidas, redirige a https://gestion.salchimonster.com/tasks/
  • No muestra interfaz de login cuando hay parámetros GET
http://localhost:8000/login?username={username}&password={password}

Nota: Reemplazar {username} y {password} con las credenciales reales del usuario.

2. Login con Formulario POST

POST /login
  • Si las credenciales son válidas, redirige a / (dashboard)
  • Si las credenciales son inválidas, redirige a https://gestion.salchimonster.com/tasks/

3. Login Directo Admin

GET /admin/login
  • Cierra cualquier sesión existente
  • Autentica automáticamente como admin usando credenciales por defecto
  • Si falla, redirige a /login

Logout

GET /logout
  • Cierra la sesión actual
  • Elimina la cookie de sesión
  • Redirige a https://gestion.salchimonster.com/tasks/

Sincronización de Usuarios

El sistema sincroniza usuarios automáticamente desde:

  • URL: https://backend.salchimonster.com/employers-basic
  • Frecuencia: Cada hora (3600 segundos) o cuando se fuerza manualmente
  • Variable de entorno: EMPLOYERS_SYNC_TTL_SECONDS (por defecto: 3600)

Contraseñas de usuarios sincronizados:

Se generan automáticamente desde el DNI: {DNI_invertido}---{DNI}

Ejemplo: DNI 1003153254 → Contraseña: 4523513001---1003153254

3. Roles y Permisos

Sistema de roles: 18 de marzo de 2025 | Restricciones avanzadas: 12 de diciembre de 2025

Roles Disponibles

  1. ADMIN: Administrador del sistema
  2. MANAGER: Gerente (mismo nivel de permisos que ADMIN)
  3. USER: Usuario regular
  4. Roles personalizados: Basados en la posición del empleado (ej: "JEFE DE COCINA")

Permisos por Rol

ADMIN / MANAGER

Pueden:

  • Acceder a todas las páginas administrativas (/admin/users, /admin/teams)
  • Ver todos los proyectos (incluso si no están asignados)
  • Sincronizar usuarios manualmente
  • Promover/degradar usuarios (con restricción: no pueden degradar el último admin activo)
  • Asignar usuarios a proyectos (además del creador)

No pueden:

  • Degradar el último administrador activo del sistema

USER (Usuario Regular)

Pueden:

  • Ver proyectos a los que están asignados
  • Gestionar tareas asignadas (iniciar, pausar, completar, reabrir)
  • Subir evidencias para tareas asignadas
  • Ver información de proyectos asignados

No pueden:

  • Crear proyectos
  • Agregar tareas a proyectos
  • Asignar usuarios a proyectos
  • Acceder a páginas administrativas
  • Ver proyectos no asignados

4. Gestión de Proyectos

CRUD básico: 22 de marzo de 2025 | Permisos de creador: 8 de noviembre de 2025

Creación de Proyectos

Quién puede crear: Cualquier usuario autenticado

POST /api/projects/create

Campos requeridos:

  • name: Nombre del proyecto
  • area_id: ID del área (opcional, usa área por defecto si no se proporciona)
  • group_id: ID del grupo (opcional, usa grupo por defecto si no se proporciona)
  • description: Descripción del proyecto (opcional)
  • deadline: Fecha límite (opcional)
  • assigned_users: Lista de IDs de usuarios asignados (opcional)

Comportamiento: El usuario que crea el proyecto se convierte automáticamente en el creador del proyecto (created_by). El creador tiene permisos exclusivos sobre el proyecto.

Visualización de Proyectos

Quién puede ver un proyecto:

  • El creador del proyecto
  • Administradores (ADMIN/MANAGER)
  • Usuarios asignados al proyecto

Restricción: Si un usuario no es admin y no está asignado al proyecto, recibe error 403

Edición y Eliminación

Quién puede editar/eliminar:

  • El creador del proyecto
  • Administradores

5. Gestión de Tareas

Tareas básicas: 28 de marzo de 2025 | Subtareas: 10 de abril de 2025 | Temporizadores: 15 de mayo de 2025 | Restricciones completas: 12 de diciembre de 2025

Creación de Tareas

Tareas Raíz

Quién puede crear: Solo el creador del proyecto

POST /api/projects/{project_id}/tasks

Restricciones:

  • No se pueden crear tareas con archivos adjuntos al momento de la creación
  • Los archivos deben agregarse después de crear la tarea

Subtareas

Quién puede crear: Solo el creador del proyecto

POST /api/projects/{project_id}/tasks/{parent_id}/child

Restricciones:

  • No se pueden agregar subtareas a tareas completadas
  • No se pueden crear subtareas con archivos adjuntos al momento de la creación

Asignación de Usuarios a Tareas

Quién puede asignar: Solo el creador del proyecto

POST /api/tasks/{task_id}/assign_users

Restricciones:

  • Solo se pueden asignar usuarios que ya estén asignados al proyecto
  • No se pueden asignar usuarios que no pertenezcan al proyecto

Gestión de Tareas

Iniciar Temporizador

Quién puede iniciar: Solo usuarios asignados a la tarea

Restricciones:

  • No se puede iniciar una tarea padre que tenga subtareas (solo se pueden iniciar las subtareas)
  • Para subtareas:
    • Si la subtarea no tiene asignación, el usuario debe estar asignado a la tarea padre
    • Si la subtarea tiene asignación, solo el usuario asignado puede iniciarla

Pausar Temporizador

Quién puede pausar: Solo usuarios asignados a la tarea

Restricciones:

  • No se puede pausar una tarea padre que tenga subtareas
  • La tarea debe estar en estado "running" para poder pausarla
  • Para subtareas: mismas reglas que iniciar

Completar Tarea

Quién puede completar: Solo usuarios asignados a la tarea

Restricciones:

  • Todas las subtareas deben estar completadas antes de completar la tarea padre
  • La tarea debe haber iniciado su temporizador al menos una vez (tener tiempo acumulado > 0)
  • Se puede agregar un comentario opcional al completar
  • Se pueden subir múltiples archivos como evidencia al completar

Reabrir Tarea

Quién puede reabrir: Solo usuarios asignados a la tarea

Restricciones:

  • Solo se pueden reabrir tareas completadas
  • Se requiere una justificación (opcional, si no se proporciona se usa un texto por defecto)
  • Se pueden subir múltiples archivos como evidencia de reapertura
  • Al reabrir una tarea padre, también se reabren automáticamente todas sus subtareas

Archivos Adjuntos a Tareas

Quién puede agregar: Solo el creador del proyecto

POST /api/tasks/{task_id}/attachments

Quién puede eliminar: Solo quien subió el archivo (verificado por uploaded_by)

DELETE /api/tasks/{task_id}/attachments/{attachment_id}

7. Gestión de Usuarios

Sincronización: 25 de marzo de 2025 | Promoción de usuarios: 3 de julio de 2025

Sincronización de Usuarios

Quién puede sincronizar: Solo administradores

POST /api/users/sync

Comportamiento: Fuerza una sincronización inmediata desde el backend externo. Actualiza usuarios existentes y crea nuevos usuarios. Desactiva usuarios que ya no están en el backend. No sobrescribe usuarios con role_locked: true (promovidos manualmente).

Creación Manual de Usuarios

Estado: DESHABILITADO

Los usuarios solo se pueden crear mediante sincronización desde el backend.

Promoción/Degradación de Usuarios

Quién puede promover/degradar: Solo administradores

POST /api/users/{user_id}/promote

Restricciones:

  • No se puede degradar el último administrador activo del sistema
  • Los roles válidos son: ADMIN, MANAGER, USER
  • Al promover un usuario, su rol se marca como role_locked: true para evitar que la sincronización lo sobrescriba

8. Restricciones y Validaciones

Validaciones básicas: 5 de abril de 2025 | Restricciones completas: 12 de diciembre de 2025

Restricciones de Tareas

Jerarquía de Tareas

  • Las tareas pueden tener múltiples niveles de subtareas
  • Una tarea padre no puede iniciarse si tiene subtareas (solo las subtareas se pueden iniciar)
  • El tiempo de una tarea padre es la suma del tiempo de todas sus subtareas
  • Una tarea padre no puede completarse hasta que todas sus subtareas estén completadas

Completado de Tareas

Condiciones obligatorias:

  1. Todas las subtareas deben estar completadas (si las hay)
  2. La tarea debe haber iniciado su temporizador al menos una vez
  3. El usuario debe estar asignado a la tarea

Opcional: Comentario de completado y archivos de evidencia

Restricciones de Archivos

  • Se aceptan todos los tipos de archivos
  • Los archivos de imagen se pueden previsualizar
  • Se pueden subir múltiples archivos simultáneamente
  • Se muestra progreso de carga para cada archivo

9. Flujos de Trabajo

Documentado: 20 de agosto de 2025 | Actualizado: 10 de enero de 2026

Flujo de Creación de Proyecto

  1. Usuario autenticado crea un proyecto
  2. El usuario se convierte automáticamente en el creador
  3. El creador puede asignar usuarios al proyecto
  4. El creador puede agregar tareas al proyecto
  5. Los usuarios asignados pueden gestionar las tareas asignadas

Flujo de Gestión de Tarea

  1. Creador del proyecto crea una tarea
  2. Creador del proyecto asigna usuarios a la tarea (solo usuarios del proyecto)
  3. Usuario asignado inicia el temporizador de la tarea
  4. Usuario asignado trabaja en la tarea (el temporizador corre)
  5. Usuario asignado puede pausar/reanudar el temporizador
  6. Usuario asignado completa la tarea (con comentario y evidencias opcionales)
  7. Si es necesario, usuario asignado puede reabrir la tarea con justificación

Modelo JSON: 13 de marzo de 2025 | Esquema PostgreSQL: 10 de enero de 2026 (futuro)

Modelo Actual (JSON)

El sistema actual utiliza almacenamiento en archivos JSON planos. La estructura de datos se basa en modelos Pydantic que garantizan la validación y consistencia de los datos.

Estructura de Archivos

  • data/users.json: Usuarios y sesiones
  • data/index.json: Índice global (áreas, grupos, mapeo de proyectos)
  • data/teams.json: Equipos de trabajo
  • data/projects/{project_id}.json: Archivo individual por proyecto

Modelo Futuro (PostgreSQL)

Nota: Este esquema está diseñado para una futura migración a PostgreSQL. El sistema actual funciona con JSON plano, pero este esquema SQL está listo para cuando se requiera escalabilidad y rendimiento mejorado.

Esquema de Base de Datos

-- ============================================ -- Sistema de Gestión de Proyectos -- Esquema PostgreSQL (Futuro) -- ============================================ -- Extensión para UUIDs CREATE EXTENSION IF NOT EXISTS "uuid-ossp"; -- ============================================ -- TABLA: users -- ============================================ CREATE TABLE users ( id VARCHAR(50) PRIMARY KEY, username VARCHAR(100) UNIQUE NOT NULL, display_name VARCHAR(200) NOT NULL, email VARCHAR(255), role VARCHAR(50) NOT NULL DEFAULT 'USER', role_locked BOOLEAN DEFAULT FALSE, is_active BOOLEAN DEFAULT TRUE, salt VARCHAR(64) NOT NULL, password_hash VARCHAR(128) NOT NULL, password_sig VARCHAR(64), dni VARCHAR(20), gender VARCHAR(20), position VARCHAR(100), site_name VARCHAR(100), external_id INTEGER, created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(), created_by VARCHAR(50) ); CREATE INDEX idx_users_username ON users(username); CREATE INDEX idx_users_role ON users(role); CREATE INDEX idx_users_is_active ON users(is_active); CREATE INDEX idx_users_dni ON users(dni); -- ============================================ -- TABLA: sessions -- ============================================ CREATE TABLE sessions ( id VARCHAR(100) PRIMARY KEY, user_id VARCHAR(50) NOT NULL REFERENCES users(id) ON DELETE CASCADE, created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(), last_seen TIMESTAMP WITH TIME ZONE DEFAULT NOW() ); CREATE INDEX idx_sessions_user_id ON sessions(user_id); CREATE INDEX idx_sessions_last_seen ON sessions(last_seen); -- ============================================ -- TABLA: areas -- ============================================ CREATE TABLE areas ( id VARCHAR(50) PRIMARY KEY, name VARCHAR(200) NOT NULL, description TEXT, created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(), created_by VARCHAR(50) ); CREATE INDEX idx_areas_name ON areas(name); -- ============================================ -- TABLA: groups -- ============================================ CREATE TABLE groups ( id VARCHAR(50) PRIMARY KEY, name VARCHAR(200) NOT NULL, area_id VARCHAR(50) NOT NULL REFERENCES areas(id) ON DELETE CASCADE, description TEXT, created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(), created_by VARCHAR(50) ); CREATE INDEX idx_groups_area_id ON groups(area_id); CREATE INDEX idx_groups_name ON groups(name); -- ============================================ -- TABLA: projects -- ============================================ CREATE TABLE projects ( id VARCHAR(50) PRIMARY KEY, name VARCHAR(200) NOT NULL, description TEXT, area_id VARCHAR(50) NOT NULL REFERENCES areas(id), group_id VARCHAR(50) NOT NULL REFERENCES groups(id), deadline TIMESTAMP WITH TIME ZONE, created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(), created_by VARCHAR(50) NOT NULL REFERENCES users(id), dirty BOOLEAN DEFAULT FALSE ); CREATE INDEX idx_projects_area_id ON projects(area_id); CREATE INDEX idx_projects_group_id ON projects(group_id); CREATE INDEX idx_projects_created_by ON projects(created_by); CREATE INDEX idx_projects_deadline ON projects(deadline); -- ============================================ -- TABLA: project_users (Relación Many-to-Many) -- ============================================ CREATE TABLE project_users ( project_id VARCHAR(50) NOT NULL REFERENCES projects(id) ON DELETE CASCADE, user_id VARCHAR(50) NOT NULL REFERENCES users(id) ON DELETE CASCADE, PRIMARY KEY (project_id, user_id) ); CREATE INDEX idx_project_users_project_id ON project_users(project_id); CREATE INDEX idx_project_users_user_id ON project_users(user_id); -- ============================================ -- TABLA: tasks -- ============================================ CREATE TABLE tasks ( id VARCHAR(50) PRIMARY KEY, project_id VARCHAR(50) NOT NULL REFERENCES projects(id) ON DELETE CASCADE, parent_id VARCHAR(50) REFERENCES tasks(id) ON DELETE CASCADE, title VARCHAR(500) NOT NULL, description TEXT, status VARCHAR(20) NOT NULL DEFAULT 'pending', accumulated_sec INTEGER DEFAULT 0, started_at TIMESTAMP WITH TIME ZONE, completed_at TIMESTAMP WITH TIME ZONE, completed_by VARCHAR(50) REFERENCES users(id), completion_comment TEXT, created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(), level INTEGER DEFAULT 0, -- Nivel de anidación (0 = raíz) path TEXT, -- Ruta jerárquica (ej: "1/2/3") CONSTRAINT chk_task_status CHECK (status IN ('pending', 'running', 'paused', 'completed')) ); CREATE INDEX idx_tasks_project_id ON tasks(project_id); CREATE INDEX idx_tasks_parent_id ON tasks(parent_id); CREATE INDEX idx_tasks_status ON tasks(status); CREATE INDEX idx_tasks_path ON tasks(path); CREATE INDEX idx_tasks_completed_by ON tasks(completed_by); -- ============================================ -- TABLA: task_users (Relación Many-to-Many) -- ============================================ CREATE TABLE task_users ( task_id VARCHAR(50) NOT NULL REFERENCES tasks(id) ON DELETE CASCADE, user_id VARCHAR(50) NOT NULL REFERENCES users(id) ON DELETE CASCADE, PRIMARY KEY (task_id, user_id) ); CREATE INDEX idx_task_users_task_id ON task_users(task_id); CREATE INDEX idx_task_users_user_id ON task_users(user_id); -- ============================================ -- TABLA: attachments -- ============================================ CREATE TABLE attachments ( id VARCHAR(50) PRIMARY KEY, filename VARCHAR(500) NOT NULL, original_name VARCHAR(500) NOT NULL, url VARCHAR(1000) NOT NULL, size BIGINT NOT NULL, content_type VARCHAR(100), uploaded_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(), uploaded_by VARCHAR(50) NOT NULL REFERENCES users(id), project_id VARCHAR(50) REFERENCES projects(id) ON DELETE CASCADE, task_id VARCHAR(50) REFERENCES tasks(id) ON DELETE CASCADE, attachment_type VARCHAR(50) DEFAULT 'attachment', -- 'attachment', 'completion_evidence', 'reopen_evidence' CONSTRAINT chk_attachment_context CHECK ( (project_id IS NOT NULL AND task_id IS NULL) OR (project_id IS NULL AND task_id IS NOT NULL) ) ); CREATE INDEX idx_attachments_project_id ON attachments(project_id); CREATE INDEX idx_attachments_task_id ON attachments(task_id); CREATE INDEX idx_attachments_uploaded_by ON attachments(uploaded_by); CREATE INDEX idx_attachments_type ON attachments(attachment_type); -- ============================================ -- TABLA: log_entries -- ============================================ CREATE TABLE log_entries ( id VARCHAR(50) PRIMARY KEY, project_id VARCHAR(50) NOT NULL REFERENCES projects(id) ON DELETE CASCADE, task_id VARCHAR(50) REFERENCES tasks(id) ON DELETE CASCADE, text TEXT NOT NULL, created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(), created_by VARCHAR(50) NOT NULL REFERENCES users(id), attachment_id VARCHAR(50) REFERENCES attachments(id) ON DELETE SET NULL, action_type VARCHAR(50) -- 'task_start', 'task_pause', 'task_complete', 'task_create', 'log_entry', etc. ); CREATE INDEX idx_log_entries_project_id ON log_entries(project_id); CREATE INDEX idx_log_entries_task_id ON log_entries(task_id); CREATE INDEX idx_log_entries_created_at ON log_entries(created_at DESC); CREATE INDEX idx_log_entries_action_type ON log_entries(action_type); -- ============================================ -- TABLA: teams -- ============================================ CREATE TABLE teams ( id VARCHAR(50) PRIMARY KEY, name VARCHAR(200) NOT NULL, description TEXT, created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(), created_by VARCHAR(50) NOT NULL REFERENCES users(id) ); CREATE INDEX idx_teams_created_by ON teams(created_by); CREATE INDEX idx_teams_name ON teams(name); -- ============================================ -- TABLA: team_members (Relación Many-to-Many) -- ============================================ CREATE TABLE team_members ( team_id VARCHAR(50) NOT NULL REFERENCES teams(id) ON DELETE CASCADE, user_id VARCHAR(50) NOT NULL REFERENCES users(id) ON DELETE CASCADE, PRIMARY KEY (team_id, user_id) ); CREATE INDEX idx_team_members_team_id ON team_members(team_id); CREATE INDEX idx_team_members_user_id ON team_members(user_id); -- ============================================ -- VISTAS ÚTILES -- ============================================ -- Vista: Proyectos con información de área y grupo CREATE VIEW v_projects_detail AS SELECT p.*, a.name AS area_name, g.name AS group_name, u.display_name AS creator_name, COUNT(DISTINCT pu.user_id) AS assigned_users_count, COUNT(DISTINCT t.id) AS tasks_count FROM projects p LEFT JOIN areas a ON p.area_id = a.id LEFT JOIN groups g ON p.group_id = g.id LEFT JOIN users u ON p.created_by = u.id LEFT JOIN project_users pu ON p.id = pu.project_id LEFT JOIN tasks t ON p.id = t.project_id GROUP BY p.id, a.name, g.name, u.display_name; -- Vista: Tareas con información del proyecto CREATE VIEW v_tasks_detail AS SELECT t.*, p.name AS project_name, COUNT(DISTINCT tu.user_id) AS assigned_users_count, COUNT(DISTINCT c.id) AS children_count FROM tasks t LEFT JOIN projects p ON t.project_id = p.id LEFT JOIN task_users tu ON t.id = tu.task_id LEFT JOIN tasks c ON c.parent_id = t.id GROUP BY t.id, p.name; RETURN NEW; END; $$ LANGUAGE plpgsql; -- Trigger: Actualizar last_seen automáticamente CREATE TRIGGER trigger_update_session_last_seen AFTER INSERT ON sessions FOR EACH ROW EXECUTE FUNCTION update_session_last_seen(); -- Función: Calcular tiempo total de tarea (incluyendo subtareas) CREATE OR REPLACE FUNCTION calculate_task_total_time(task_id_param VARCHAR) RETURNS INTEGER AS $$ DECLARE total_seconds INTEGER; BEGIN WITH RECURSIVE task_tree AS ( SELECT id, accumulated_sec, started_at FROM tasks WHERE id = task_id_param UNION ALL SELECT t.id, t.accumulated_sec, t.started_at FROM tasks t INNER JOIN task_tree tt ON t.parent_id = tt.id ) SELECT COALESCE(SUM( accumulated_sec + CASE WHEN started_at IS NOT NULL AND status = 'running' THEN EXTRACT(EPOCH FROM (NOW() - started_at))::INTEGER ELSE 0 END ), 0) INTO total_seconds FROM task_tree; RETURN total_seconds; END; $$ LANGUAGE plpgsql; -- ============================================ -- ÍNDICES ADICIONALES PARA RENDIMIENTO -- ============================================ -- Índice compuesto para búsquedas frecuentes CREATE INDEX idx_projects_area_group ON projects(area_id, group_id);   • Se incluyen vistas materializadas para consultas frecuentes
